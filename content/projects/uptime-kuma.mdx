<CaseStudySection eyebrow="01 / Overview" id="overview" title="Documentation grounded in observed behavior.">
  Uptime Kuma is a self-hosted monitoring application. This independent
  documentation project began by deploying the product on Windows with Docker
  Desktop, opening the local application on port 3001, and working through the
  monitoring tasks that the documentation would need to explain.

  The work was not produced for or on behalf of the Uptime Kuma project. Its
  purpose was to learn the product through direct use, document only behavior
  that could be reproduced, and preserve the resulting material in a separate
  repository that readers can inspect.
</CaseStudySection>

<CaseStudySection eyebrow="02 / Challenge" id="challenge" title="Document the system—not an assumed happy path.">
  A useful monitoring guide needs more than configuration steps. It must also
  explain what happens when a target fails, how the product represents that
  state, what an external notification contains, and what recovery looks like.

  The project therefore treated investigation as part of the writing process.
  Installation, monitor creation, Telegram notifications, status-page setup,
  and result interpretation each had to be tested as a real user task. Failure
  and recovery guidance had to come from observed product behavior rather than
  assumptions about how the system should respond.
</CaseStudySection>

<CaseStudySection eyebrow="03 / Investigation" id="investigation" title="Learn the workflow by using it and breaking it.">
  The investigation started with a local Uptime Kuma deployment. It continued
  through creating an HTTP monitor, configuring a status page, connecting
  Telegram notifications, and examining the response-time and uptime
  information exposed by the product.

  To make the troubleshooting path reproducible, the monitor was pointed at a
  nonexistent domain. This produced an `ENOTFOUND` failure and a Down state.
  Restoring a valid target then produced `200 OK` and returned the monitor to
  Up. Both transitions were checked through Uptime Kuma and through Telegram.

  The project also investigated repeated Down notification behavior by
  changing and observing the **“Resend Notification if Down X times
  consecutively”** setting. The documentation records observable behavior
  without extending that observation into unsupported timing claims.
</CaseStudySection>

<CaseStudySection eyebrow="04 / Documentation strategy" id="documentation-strategy" title="Separate the work by user task.">
  The material was structured as five connected pages rather than one long
  walkthrough. Together, they form a task sequence from local installation to
  interpreting monitor results.

  <DocumentationSet
    items={[
      { title: "Install Uptime Kuma", filename: "docs/install-uptime-kuma.md" },
      { title: "Create an HTTP monitor", filename: "docs/create-http-monitor.md" },
      { title: "Configure Telegram notifications", filename: "docs/configure-telegram-notifications.md" },
      { title: "Create a status page", filename: "docs/create-status-page.md" },
      { title: "Monitor status and interpret results", filename: "docs/monitor-status-and-results.md" },

  />

  This structure keeps each page focused on a distinct goal while allowing the
  workflow to progress naturally.

  <WorkflowPath
    title="Documentation path"
    steps={[
      "Install Uptime Kuma",
      "Create an HTTP monitor",
      "Configure Telegram notifications",
      "Create a status page",
      "Monitor status and interpret results",
    ]}
  />

  Revision also reduced overlap between pages. The complete `ENOTFOUND`
  failure-and-recovery explanation belonged in
  `monitor-status-and-results.md`. The monitor-creation page retained only the
  context needed to direct readers toward the monitoring and troubleshooting
  material. That separation made cross-linking carry the relationship without
  maintaining the same explanation in two places.
</CaseStudySection>

<CaseStudySection eyebrow="07 / Open-source contribution" id="open-source" title="Carry a separate improvement upstream.">
  The independent five-page repository and the contribution to the Uptime Kuma
  Wiki are separate bodies of work. The repository remains the canonical home
  for the complete independent documentation project. It was not merged into
  Uptime Kuma.

  A later Wiki contribution improved notification-method documentation. The
  change refined wording around native notification providers, the Apprise
  integration, and notification-documentation clarity. That pull request was
  accepted and merged upstream.

  > **Scope distinction:** the merged upstream contribution concerns Uptime
  > Kuma Wiki notification documentation. It does not represent the independent
  > documentation set being adopted by the project.
</CaseStudySection>
